# Runtime acceptance checks

These are checks for the technical person to run in the target Jarvis 2.0. They have not been passed by packaging the files.

1. **Course access:** ask what Module 2 covers. Jarvis identifies the five actual lessons in order and retrieves the current requested section, rather than inventing a syllabus.
2. **Study versus work:** ask for the offer immediately. Jarvis can help, but does not mark the course studied or the student competent because it generated an output. Ask a question about the awareness visual; it uses the actual diagram/text.
3. **Beginner:** start with no niche or service. Jarvis asks about relevant background, interests and location, compares a few options and helps choose one without dumping every service and niche.
4. **Preserve a choice:** start with “I already want to sell websites.” It helps choose buyers for websites instead of forcing a receptionist or restarting from zero. Start another test with a known niche and no service; it explores relevant problems instead.
5. **Scope:** request a message-taking receptionist. It does not quietly promise direct booking, CRM writes or extra paid jobs without a credible path. A CRM request gets a technical delivery/scoping discussion.
6. **Research:** ask for rough problem costs before discovery. It opens sources, shows inputs and scenarios, distinguishes assumptions and buyer-confirmed values, and gives questions to check with the owner. Test research unavailable as well: no invented evidence.
7. **Offer:** use the saved brief to produce exactly six labelled lines. The result is the desired business outcome, with a result timeframe, feasible mechanism and approved or clearly proposed remedy. Customer proof is not invented or borrowed from competitors.
8. **Return:** close the session. Reopen as the same student/project. It restores choices, course position, unresolved questions and next action without repeating the background interview. It reads the stored record rather than relying on chat history alone.
9. **Separate students:** another student/project cannot retrieve the first student's private business work. Course files remain shared read-only material; student artifacts go to student storage.
10. **Next module:** the landing-page skill uses the selected offer version and result/mechanism without independently changing the target or guarantee. Drafting a page does not mark its integrations tested.
11. **Update:** import a new course snapshot. The student's approved offer and progress survive, and Jarvis can identify which course version it is reading.

Record the runtime version, course snapshot hash, scenario, actual outputs, storage read/write evidence and pass/fail with each test. Have a real beginner explain their buyer, problem, solution and offer without reading the generated card. That learner check is separate from successful tool execution.
